# 小程序前端开发验证工作流（Mandatory Workflow）

> 适用对象：所有对 `apps/miniapp`（FISH 微信小程序，Taro 4 + React）的**前端改动** —— 无论是人还是 AI agent。
> 这是一条**强制规则**，不是建议：小程序端上没有自动化测试基建，端上验证只能靠人/agent 在微信开发者工具里做。
> 端上验证优先级：**微信开发者工具 > 真机实机 > 其它一切**。H5/纯代码层面的检查**不能替代**微信开发者工具里的验证。

---

## 0. 为什么必须这样

小程序是**端上运行时**：原生 TabBar、自绘导航、真机字体、safe-area、`navigationStyle: custom` 的布局，
在浏览器 / 命令行里看不出真实效果。只靠看代码、跑 typecheck、或 H5 预览就认为"做好了",会
漏掉大量真实机型上才暴露的问题。因此**一批改动合并前，必须回到微信开发者工具里过一遍**。

---

## 1. 一批页面 = 一条分支 = 一个 PR

- **一个 PR 可以包含一个或多个页面**（含它们的样式、组件、交互逻辑）。按一次要交付的范围开**一条**分支，不要为每个页面拆一条分支/一个 PR。
- 分支命名：`feat/miniapp-<要点>-<序号>`；一批里有多个页面时把要点串起来即可，例如
  `feat/miniapp-home-detail-searchcap-3`。
- 分支从**最新 `origin/main`** 切出，保证基线最新。
- **一个 PR 讲一件事**：不要夹带与本批交付无关的重构，避免 review 与回滚纠缠；同批内多页面是允许的。

---

## 2. 同一时间只开一个 PR（门禁在 PR 粒度上）

- 上一个小程序 PR **合并、或被 Owner 明确确认**之前，**不再新开下一个小程序 PR**。
- **同一条 PR 内可以继续追加同批页面**，不需要为加一个页面重新走门禁。
- 判断方法：

  ```bash
  gh pr list -R zzstar101/FISH --state open --search 'head:feat/miniapp-'
  ```

  有多条自己未收口的小程序 PR 时，先把旧的收口，而不是并行铺开。

---

## 3. 本流程的适用范围

- 本文与 [apps/miniapp/AGENTS.md](../apps/miniapp/AGENTS.md) **只约束 `apps/miniapp`**。
- `apps/web`（移动端 PWA）与 `apps/web-pc`（PC 站）**没有微信端运行时**，不受本文门禁约束：它们按根 [AGENTS.md](../AGENTS.md) 的通用纪律走（最小改动 + `typecheck` / `lint` / `test` + CI 全绿 + 审查意见逐条处理），一个 PR 也可以包含多个页面。

---

## 4. 合并前通过演示验证

小程序 PR 在**合并前**必须满足**全部**：

1. **微信开发者工具里逐页演示通过**：改动后打开本批涉及的每个页面，
   - 真机渲染正常（无白屏、无排版错乱）；
   - 交互（点击、输入、跳转、弹层、loading/error 态）符合预期；
   - 与设计稿/上一版相比没有引入明显视觉回归。
2. **Owner 确认效果可行**：把演示结果（截图 / 描述 / 现象）给 Owner，Owner 认可后才合并。
   - **"演示通过 + Owner 认可" 是合并的必要前置条件**，两者缺一不可。
3. **静态检查通过**：`bun run --filter '@fish/miniapp' typecheck` 与 `bun run lint` 无错误。
4. 提交信息用 Conventional Commits，遵守 `CONTRIBUTING.md`。

> 顺序：改代码 →（开 PR、CI 变绿）→ 微信开发者工具逐页演示 → Owner 认可 → 合并。
> **提交与推送本身不再是演示的前置条件** —— 端上演示是**合并前**的一次门禁，不是每次 commit 的关卡，也不是"动手前先报备"。

---

## 5. 兜底与特例

- **纯文档 / 纯配置 / 纯类型**变更（不涉及任何渲染或交互），可豁免微信开发者工具演示，
  但仍受第 2 节的 PR 粒度门禁约束。
- **不确定是否算"页面改动"时，按"算"处理** —— 宁可多验证，不可漏验证。
- 微信开发者工具不可用时（本地没装 / 未登录），**视为阻塞**：如实告知 Owner 无法端上验证，
  **不擅自以 H5 或纯代码检查充当端上验证**，也不在未演示的情况下合并。
- 本工作流**不要求**改动前预先报备或等待批准：直接改、直接开 PR，用演示与 review 收口即可。

---

## 6. 一句话总结

**一批小程序页面 = 一条分支 = 一个 PR；同一时间只开一个 PR；合并前在微信开发者工具里逐页演示、Owner 认可、`typecheck`/`lint` 通过。**
